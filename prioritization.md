# Приоритизация по MoSCoW

Primary-персона (по `personas.md`): **Compliance Officer**. Критерии Must have: (1) фича напрямую связана с её JTBD, (2) без неё основной сценарий (разбор кейса) невозможен, (3) table stakes — есть у всех конкурентов, ожидается по умолчанию.

## Must have

Без этого запуск бессмысленен — продукт не решает основную задачу primary-персоны.

| Фича | Почему Must |
|---|---|
| KYC / ID-верификация (Sumsub) | Table stakes; без источника данных кейса не существует |
| AML / санкции / PEP screening (ComplyAdvantage) | Table stakes; ядро JTBD «решить, безопасен ли клиент» |
| Матрица риск-тиров (Low/Medium/High) с эскалацией | Прямая связь с JTBD Compliance Officer; ключевой дифференциатор |
| Auto-одобрение Low с фиксацией в аудит-логе | Часть механики риск-тиров — без него Low-ветка не функционирует |
| Soft-block Medium с SLA | Часть механики риск-тиров |
| Жёсткое вето High | Часть механики риск-тиров |
| 4-eyes: роль Senior Compliance Officer + статус «Ожидает подтверждения» (базовая версия) | Ядро продуктовой идентичности и регуляторного позиционирования (SCHUFA/GDPR ст.22); подтверждено интервью как частая реальная потребность |
| Состояния кейса (полный жизненный цикл) | Без явных статусов основной сценарий не работает |
| Экран разбора кейса с прогрессивным раскрытием | Это и есть основной сценарий (brief.md, 3.1) |
| Explainability-блок AI-вердикта в карточке | Ядро JTBD «защитимое решение»; регуляторное требование (EU AI Act) |
| Явный показ расхождения источников | Прямой ответ на документированную боль Compliance Officer (ручная сверка); ключевой дифференциатор |
| Аудит-лог (кто/когда/что + версия модели/входные данные) | Без него решение не защитимо перед аудитом — JTBD не выполняется |
| Accessibility WCAG 2.1 AA + риск не только цветом | Явное требование брифа; подтверждённый реальный баг у конкурента (audit_report.md) |
| Дизайн-система с нуля | Инфраструктурный блокер — без неё нельзя построить остальное |

## Should have

Важно, но запуститься можно и без. Добавляем сразу после MVP.

| Фича | Почему Should, не Must |
|---|---|
| Внутренний поведенческий скоринг (3-й источник) | Требует данных о реальных кейсах для обучения модели, которых до запуска ещё нет |
| Confirm-диалог перед значимыми решениями | Важная защита от ошибок, но основной сценарий технически работает и без неё |
| Полный список правил (сработавших/несработавших) в карточке | Улучшение полноты, MVP может показывать только сработавшие |
| Три статуса решения в аудит-логе (авто/human/timeout) | Требует, чтобы базовый 4-eyes-механизм (Must) уже работал и накопил реальные кейсы timeout |
| Лёгкий паттерн «второе мнение» | Отдельный от формального 4-eyes флоу; интервью показало частую потребность, но не блокирует базовый сценарий |
| Маршрутизация эскалации на роль/группу | MVP может стартовать с одним фиксированным Senior Compliance Officer на аккаунт |
| SLA-таймер эскалации с обоснованием | Нужна начальная статистика по реальным эскалациям, чтобы откалибровать таймер честно |
| Явная эскалация при истечении SLA | Зависит от SLA-таймера |
| Пассивный индикатор «Ожидает подтверждения» | UI-полировка поверх базового статуса (Must) |
| Очередь кейсов сворачивает Low-риск по умолчанию | UX-улучшение очереди, не блокирует разбор отдельного кейса |
| Дашборд CPO с одним CTA | CPO — secondary-персона, не блокирует сценарий Compliance Officer |
| Override rate + onboarding conversion на одном экране | CPO-facing, secondary |
| Виджет прогноза счёта / bill shock алерты | Важно для удержания при росте usage, но не для первого запуска с малым числом клиентов |
| Метрики OKR (Time-to-decision, FP rate) — полноценный дашборд | Базовый трекинг нужен с первого дня внутренне, но user-facing дашборд — не Must |
| No-code конструктор риск-правил | Брифом явно решено: матрица единая для MVP, кастомизация вне скоупа |
| Непрерывный (perpetual) мониторинг | Брифом явно выбран периодический re-review для MVP; непрерывный — апгрейд |

## Could have

Полезно, но не критично. Если есть время и ресурс.

| Фича | Комментарий |
|---|---|
| Перевод compliance-метрик на язык бизнеса для CPO | Полировка коммуникации, не меняет функциональность |
| Read-only импорт исторических кейсов при миграции | Удобство онбординга клиента, можно решить вручную/через CSV на старте |
| Публикация override rate как метрики-дифференциатора | Маркетинговый ход, не продуктовая функциональность как таковая |

## Won't have (now)

Осознанно откладываем. Не в этой версии.

| Фича | Почему не сейчас |
|---|---|
| Self-serve вход / публичная цена | Открытый GTM-вопрос, не решён в брифе. Дефолт для MVP: sales-assisted онбординг — безопаснее для compliance-тяжёлого продукта, пока решение не принято явно |
| Облегчённый demo-дашборд до контакта с sales | Зависит от нерешённого GTM-вопроса выше |
| Free tier / программа дешёвого входа | Тот же GTM-вопрос; бизнес-решение, не готовое к продуктовой реализации |
| Кастомизация риск-матрицы под юрисдикцию | Явно вне скоупа MVP по брифу (архитектурно заложено, не реализуется сейчас) |

## Организационное требование (вне MoSCoW-продукта, но блокирует бизнес)

- **DORA-готовность** (реестр контрактов, отчётность об инцидентах) — не фича для проектирования, а юридическая/операционная работа, необходимая до подписания контрактов с финансовыми клиентами. Отслеживать отдельно от продуктового скоупа.
