# Scope MVP

## Одно предложение

MVP — это инструмент для compliance-офицера растущего финтех-стартапа, который разбирает KYC/AML-кейс за один экран с прогрессивным раскрытием: видит риск-тир, явное расхождение между Sumsub и ComplyAdvantage, explainability AI-вердикта — и либо кейс закрывается автоматически (Low, с записью в аудит-лог), либо офицер решает сам (Medium/High), либо, если не согласен с AI, эскалирует формально через 4-eyes вместо неформального Slack-сообщения.

## Список фич MVP (только Must have)

1. KYC / ID-верификация (Sumsub)
2. AML / санкции / PEP screening (ComplyAdvantage)
3. Матрица риск-тиров (Low/Medium/High) с эскалацией
4. Auto-одобрение Low с фиксацией в аудит-логе
5. Soft-block Medium с SLA
6. Жёсткое вето High
7. 4-eyes: роль Senior Compliance Officer + статус «Ожидает подтверждения» (базовая версия — один назначенный человек на аккаунт, без роутинга по группе)
8. Состояния кейса (полный жизненный цикл)
9. Экран разбора кейса с прогрессивным раскрытием
10. Explainability-блок AI-вердикта в карточке
11. Явный показ расхождения источников
12. Аудит-лог (кто/когда/что + версия модели/входные данные)
13. Accessibility WCAG 2.1 AA + риск не только цветом
14. Дизайн-система с нуля

## Основной сценарий (путь Compliance Officer от входа до результата)

1. **Вход** — Compliance Officer логинится, попадает в очередь кейсов.
2. **Очередь** — видит список кейсов со статусами и риск-тирами (без сворачивания Low по умолчанию — это Should have; в MVP Low просто виден в списке уже как «Approved» с пометкой авто-решения).
3. **Открытие кейса** — кликает на кейс → видит сводку: identity-данные, риск-скор/тир (иконка + подпись, не только цвет), краткая сводка explainability.
4. **Расхождение источников** — если Sumsub и ComplyAdvantage расходятся, это видно сразу на сводке как отдельный элемент, не спрятано.
5. **Прогрессивное раскрытие** — по клику разворачиваются детали: документы, история, полный explainability-блок (версия модели, входные данные).
6. **Решение по тиру:**
   - **Low** — уже авто-одобрен, офицер просто видит это в истории с записью в аудит-логе; действие не требуется.
   - **Medium** — soft-block, офицер рассматривает в рамках SLA, нажимает Approve/Reject/RFI.
   - **High** — жёсткое вето: без явного одобрения офицера кейс не проходит. Если офицер согласен с AI-вердиктом — подтверждает. Если не согласен — переводит кейс в статус **«Ожидает подтверждения»**.
7. **4-eyes (для High, при несогласии)** — кейс уходит назначенному Senior Compliance Officer. Тот открывает тот же экран (сводка + explainability + расхождение источников + заметка первого офицера), подтверждает или отменяет вердикт.
8. **Фиксация** — решение (любого типа) записывается в аудит-лог: кто, когда, что изменил, версия AI-модели и входные данные, повлиявшие на вердикт.
9. **Закрытие** — кейс переходит в Approved/Rejected; дальнейший периодический re-review — вне экрана этого сценария (Should have для полноценного планирования цикла, в MVP жизненный цикл состояния поддержан, автоматизация повторного запуска — нет).

Экраны: Логин → Очередь кейсов → Карточка кейса (сводка + прогрессивное раскрытие) → [Экран подтверждения для Senior Compliance Officer] → История/аудит-лог кейса.

## Что осознанно НЕ входит (топ-3 из Should have — в следующей версии)

1. **Внутренний поведенческий скоринг (третий источник данных).** MVP запускается на двух внешних вендорах (Sumsub + ComplyAdvantage) с явным показом их расхождения — это уже даёт ключевой дифференциатор без риска выкатывать необученную модель. Собственный поведенческий скоринг требует накопленных данных о реальных кейсах для тренировки, которых просто нет до первого запуска. Добавляем, как только накопится достаточно исторических решений.

2. **SLA-таймер эскалации, маршрутизация на роль (не фиксированного человека) и три статуса решения в аудит-логе (авто/human/timeout).** Эти три взаимосвязанных инсайта пришли из симулированного интервью (`interview_compliance_officer.md`) и требуют, чтобы базовый механизм 4-eyes (Must have — пункт 7 выше) уже был в проде и накопил реальную статистику эскалаций. Калибровать таймер «с потолка» рискованно — сам интервьюируемый officer прямо сказал, что не примет дефолтное число без обоснования. Сначала — работающий базовый флоу, потом — калибровка по данным.

3. **Дашборд CPO (override rate, onboarding conversion, прогноз счёта/bill shock).** CPO — secondary-персона; MVP сфокусирован на ежедневном сценарии primary-персоны (Compliance Officer). Кроме того, метрики override rate и onboarding conversion бессмысленно показывать без накопленной истории использования — в момент запуска этих данных просто ещё нет. Добавляем сразу после того, как у первых клиентов накопится статистика за несколько недель использования.
