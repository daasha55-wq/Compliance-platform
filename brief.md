# Бриф: Compliance-платформа для финтех-стартапов

## 1. Контекст продукта

B2B SaaS / RegTech-платформа, объединяющая KYC, AML, проверку по санкционным спискам и соответствие GDPR/PDPA в единой подписке. Целевой сегмент — растущие финтех-стартапы; цена подписки масштабируется вместе с бизнесом клиента (комбинированная модель: seats + usage overage). Покупатели — CPO и compliance-офицеры финтех-компаний.

Ключевой дизайн-вызов: упаковать регуляторную сложность в понятный, предсказуемый workflow, обслуживая два конфликтующих приоритета — скорость (product) и безопасность (compliance) — без ущерба ни одному из них.

## 2. Целевые пользователи

| Роль | Частота использования | Основные задачи | Приоритет в UI |
|---|---|---|---|
| Compliance-офицер | Ежедневно | Разбор кейсов (KYC/AML), решения по эскалациям, работа с риск-флагами | Основной пользователь — приоритетный экран |
| Senior Compliance Officer | По требованию (4-eyes) | Подтверждение/отклонение override AI-вердикта для High-risk кейсов | Отдельная роль с правами подтверждения; второй экран — очередь «ожидает подтверждения» |
| CPO / Product Manager | Еженедельно | Обзор конверсии онбординга, узкие места, где compliance тормозит продукт | Вторичный пользователь |
| Аудитор / регулятор | Эпизодически | Не активный пользователь UI — потребляет данные аудит-лога | Не проектируется как отдельная роль; закрывается требованиями к аудит-логу (см. п.6) |

## 3. Ключевые сценарии

### 3.1 Разбор кейса (приоритетный сценарий №1)
Compliance-офицер открывает кейс → видит сводку и риск-скор (прогрессивное раскрытие) → при необходимости разворачивает детали (документы, история, санкционные совпадения) → принимает решение.

### 3.2 Матрица разрешения конфликта product ↔ compliance по уровню риска

| Уровень риска | Кто решает | Механизм |
|---|---|---|
| Low | Product | Авто-одобрение без участия compliance, **с обязательной фиксацией в аудит-логе** (иначе — слепая зона) |
| Medium | Compliance (SLA) | Soft-block — кейс на паузе до ревью в рамках SLA |
| High | Compliance | Жёсткое вето — кейс не проходит без явного одобрения compliance |

Матрица единая для всех клиентов на MVP. Кастомизация под юрисдикцию/лицензию заложена архитектурно (риск-тир — параметр, а не хардкод), но вне скоупа MVP — иначе проект превращается в конструктор правил вместо продукта для разбора кейсов.

### 3.3 Сценарий несогласия с AI-вердиктом
Compliance-офицер не согласен со скорингом AI → override недоступен в одно действие. Кейс переходит в состояние **«Ожидает подтверждения»** и уходит в очередь Senior Compliance Officer — отдельной роли в системе с правом подтвердить или отклонить override. Это удерживает решение и его причину внутри аудит-следа, не давая процессу уйти в почту/мессенджеры.

### 3.4 Состояния кейса (расширенный флоу)
Новый → На проверке → Требуется доп. информация (RFI) → Эскалация → **Ожидает подтверждения (4-eyes)** → Одобрено / Отклонено → периодический re-review.

## 4. Технические ограничения

- Платформа — orchestration-слой поверх трёх источников данных:
  - **Sumsub** — ID-верификация;
  - **ComplyAdvantage** — санкции и PEP-проверка;
  - **внутренний скоринг поведения** — собственная модель.
- Источники могут расходиться (например: один даёт 80% совпадение, другой не находит ничего). UI обязан показывать это расхождение явно, а не усреднять в единый скор — это ключевая деталь интерфейса разбора кейса, а не источник шума для упрощения.
- AI/ML используется для риск-скоринга; объяснимость вердикта (explainability) — критичное требование, обязателен UI-паттерн, показывающий, какие данные/модель привели к скору.

## 5. UI-требования

- Дизайн-система: готовой DS нет, есть только брендбук (цвета/шрифты) — компоненты создаются с нуля в рамках проекта.
- Accessibility: **WCAG 2.1 AA** — стандарт для B2B-софта, достижим и не ломает цветовую шкалу риска.
  - Цвет не единственный носитель смысла: уровень риска (Low/Medium/High) обязательно дублируется подписью и формой (иконка/паттерн) — иначе шкала нечитаема при дальтонизме.
- Плотность информации: прогрессивное раскрытие — сводка и риск-скор видны сразу, детали (документы, история, санкционные совпадения) открываются по клику/в табах.
- Обязательный паттерн: explainability-блок AI-вердикта (версия модели + входные данные, повлиявшие на скор) — виден прямо в карточке кейса, не спрятан за доп. кликами.
- Расхождение источников (Sumsub / ComplyAdvantage / внутренний скоринг) отображается как отдельный, явно читаемый элемент — не усредняется.

## 6. Аудит-лог (обязательные требования)

- Кто/когда/что изменил — все действия пользователей с timestamp и user ID, включая авто-одобрения по Low-риску.
- Версия AI-модели и входные данные, повлиявшие на конкретный вердикт.

Осознанно вне скоупа (не «не решено», а вынесено намеренно):
- Журнал согласий на обработку данных (GDPR/PDPA) — собирается на стороне клиента платформы при регистрации конечного пользователя, это другой продукт.
- История экспорта/доступа к данным — задача платформенной безопасности, отдельная подсистема.

## 7. Метрики успеха (OKR)

| Метрика | Смысл |
|---|---|
| Time-to-decision по уровням риска | Low закрывается за секунды, High может занимать дни — метрика по тирам, не усреднённая |
| False positive rate | Доля флагов, отменённых офицерами — главная боль индустрии, прямой аргумент в споре с CPO |
| Override rate по типам флага | Если конкретный тип флага регулярно отменяют — ошибается модель; связывает несогласие офицера с дашбордом CPO |
| Onboarding conversion | Метрика CPO — вторая сторона конфликта product/compliance |

Монетизация: комбинация seats + usage-overage, растёт вместе с бизнесом клиента.
